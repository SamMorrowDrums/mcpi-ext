# Decision Log

Record of key architectural and design decisions. Keep this up to date as decisions are made.

## 001 — Extension, not fork

**Date:** 2026-04-23
**Context:** Should we fork pi to build the MCP agent harness, or use the extension API?
**Decision:** Build as a pi extension. The extension API provides everything we need: `registerTool()`, `setActiveTools()`, `on("tool_result", ...)`, `exec()`, lifecycle hooks.
**Rationale:** Everything in scope (skill-gated tool visibility, football CLI, code mode, output offloading) is policy and orchestration — deciding _when_ and _how_ to expose MCP tools to the model. That's extension territory. We'd only need to fork if we needed to change pi's tool dispatch, context assembly, or model loop.

## 002 — Agent harness controls tool visibility, not MCP servers

**Date:** 2026-04-23
**Context:** How do MCP tools become visible to the model?
**Decision:** The harness (pi extension) decides what tools the model sees. MCP servers just expose their tools and optionally their skills. The harness holds all discovered tools internally and only sends them to the model when a skill names them.
**Rationale:** Maximal agent capability, minimal tokens. The model's context window isn't stuffed with every tool from every connected MCP server. Tools appear only when a skill provides the context for using them.

## 003 — Tiered access model

**Date:** 2026-04-23
**Context:** How should the model access MCP tools?
**Decision:** Three tiers of access, all complementary:

| Tier               | Mechanism                                                    | When Used                               |
| ------------------ | ------------------------------------------------------------ | --------------------------------------- |
| 1 — Skills (#1)    | Skill loaded → `allowed-tools` exact-matched → tools visible | MCP server ships skills                 |
| 2 — Football (#2)  | CLI progressive discovery → HITL for writes                  | Ad-hoc exploration, no skills           |
| 3 — Code Mode (#4) | all-tool discovery + read-only dispatch                      | Sandboxed computation and safe batching |

**Rationale:** Different situations call for different access patterns. Skills give direct access with workflow knowledge. Football gives interactive access with safety. Code mode gives autonomous access to safe operations at scale.

## 004 — Large tool output offloading

**Date:** 2026-04-23
**Context:** Tool responses can be thousands of tokens, wasting context window.
**Decision:** Offload only registered direct MCP proxy results at the proxy adapter. Textual or
structured output above 2,048 UTF-8 bytes (a deterministic approximation of ~500 tokens) is written
atomically to a private session-owned result directory and replaced with a bounded pointer and
preview. Code Mode, tool-cli, host tools, and other extension tools retain their own result handling;
the originally proposed global `pi.on("tool_result", ...)` interception is explicitly superseded
because it would rewrite unrelated execution surfaces.
**Rationale:** Controls output token cost the same way skills/football/code-mode control input token cost. The model can read the file if it needs the content.

## 005 — MCP SDK and JSON config for server connections

**Date:** 2026-04-23
**Context:** How should the extension connect to MCP servers?
**Decision:** Use the official TypeScript MCP packages with a JSON config file at `~/.config/mcpi-ext/mcp.json` (overridable via `--mcp-config` flag). The current client implementation uses the split `@modelcontextprotocol/client` package; server fixtures use `@modelcontextprotocol/server`. The config supports two transport types: `stdio` (spawns a child process) and `remote` (Streamable HTTP). A `McpClientManager` class connects to all configured servers on `session_start`, discovers tools via `tools/list`, handles tool-list changes, and disconnects on `session_shutdown`.
**Rationale:** The official MCP SDK is the canonical way to implement MCP clients. JSON config aligns with VS Code and Claude Code conventions for MCP server configuration. Supporting both stdio and remote covers local dev servers and cloud-hosted MCP endpoints. Tools are discovered and stored internally but NOT registered with pi — the access tiers (Skills #1, Football #2, Code Mode #4) decide when to expose tools to the model.

## 006 — CI model access via GITHUB_TOKEN

**Date:** 2026-04-23
**Context:** Can Pi's `github-copilot` provider use the Actions `GITHUB_TOKEN` for model inference in CI?
**Decision:** Yes. The GitHub Models API (GA since April 2025) grants model inference to the Actions `GITHUB_TOKEN` when the workflow declares `permissions: models: read`. Pi's `--provider github-copilot` uses this same API. The CI workflow declares this permission so future e2e tests can run Pi with model access without a PAT.
**Rationale:** Using the built-in `GITHUB_TOKEN` avoids storing secrets for CI model access. The `models: read` scope is the minimum required — no write access needed. This enables full trajectory e2e tests in CI (connect to MCP servers, run Pi agent, verify results).

## 007 — Custom skill registry for MCP skills, not Pi's native skill system

**Date:** 2026-04-23
**Context:** Should MCP-discovered skills use Pi's built-in `loadSkills`/`formatSkillsForPrompt` pipeline (writing SKILL.md files to disk) or a custom in-extension registry?
**Decision:** Custom `SkillRegistry` + `load_skill` tool + `formatMcpSkillsForPrompt`, styled after Pi's native skill system but fully self-contained in the extension. Skills are discovered from MCP `skill://` resources and injected into the system prompt via the `before_agent_start` hook.
**Rationale:** MCP skills live on remote servers, not on disk. Writing them to temp files would be fragile and unnecessary. The custom approach keeps MCP skills self-contained, gives us full control over the activation → tool gating flow, and avoids coupling to Pi's internal skill loader. The XML format matches Pi's `<available_skills>` pattern so models already know how to interact with it.

## 008 — Cache-safe progressive tool disclosure via `deferred` flag

**Date:** 2026-05-11
**Context:** When `load_skill` called `setActiveTools()` to reveal new tools, the tools array sent to the model changed, invalidating prompt cache. Decision 008 previously accepted this trade-off.
**Decision:** Use `deferred: true` on MCP tool proxies with provider-native support and extension-level gating:

1. **Anthropic:** pi-mono maps `deferred: true` to `defer_loading: true` in the API payload. Deferred tools stay in the tools array but are hidden from the model's view. Optional `tool_reference` content blocks can explicitly enable them on demand.
2. **OpenAI Responses:** pi-mono maps `deferred: true` to `defer_loading: true` and auto-injects `{"type": "tool_search"}` into the tools array. The model discovers deferred tools automatically via hosted server-side search — no explicit activation needed. (OpenAI's client-executed `tool_search_output` is the equivalent of Anthropic's `tool_reference`, but hosted search is sufficient for our use case.)
3. **All providers (fallback):** The extension's `tool_call` hook blocks premature calls to gated tools and returns an error message naming the relevant skill. After `load_skill` fires, tools are marked as enabled and calls go through.

**Rationale:** Both Anthropic and OpenAI natively support `defer_loading` (tested with Claude Opus 4.7 and GPT-5.4). The tools array and system prompt stay constant throughout the conversation — prompt cache is fully preserved. The `tool_call` hook provides a provider-agnostic enforcement layer for providers without native `defer_loading` support.

## 009 — tool-cli uses JSON-RPC 2.0 over HTTP on a predefined port

**Date:** 2026-04-24
**Context:** The Football CLI (issue #2) needs a communication protocol between the thin CLI binary and the extension that manages MCP connections.
**Decision:** JSON-RPC 2.0 over HTTP on `localhost:7179` (overridable via `TOOL_CLI_PORT` env var). The RPC server lives in the extension, started on `session_start` and stopped on `session_shutdown`. The CLI binary (`tool-cli`) is a thin client that uses `fetch` to call the server. No new dependencies — uses Node's `http` module for the server and global `fetch` for the client.
**Rationale:** JSON-RPC 2.0 is a standard, simple protocol that maps cleanly to the four operations needed (listServers, listTools, describeTool, callTool). HTTP is the simplest transport for request/response. A predefined port avoids coordination complexity for now. The architecture supports future HITL confirmation for non-read-only tools — the RPC server's `callTool` method is the single choke point where tool annotations can be checked and destructive calls gated through user approval.

> **Superseded in part by [015](#015--mcppolicy-is-the-single-authorization-boundary-for-every-mcp-execution-path).** The RPC server's `callTool` is not a sufficient choke point: it forwards `server`/`tool`/`args` to the provider without checking them against the discovered set, so a caller can name a tool the CLI never advertised. Authorization now lives in `McpPolicy`, behind the provider.

## 010 — tool-cli has no auth (known limitation)

**Date:** 2026-04-24
**Context:** The tool-cli RPC server listens on `127.0.0.1:7179` with no authentication. Any local process can discover and execute MCP tools through it.
**Decision:** Accept this for now as a development convenience. The server is localhost-only, which limits the blast radius to local processes, but this is not a finished security posture. Before production use, add a shared secret (e.g. a one-time token passed via environment variable from the extension to the CLI) so only the intended agent process can make calls.
**Rationale:** Adding auth now would complicate the initial implementation without changing the threat model much — the agent already has shell access and could call MCP tools through other means. But as the tool matures and especially once HITL gating is added for destructive tools, unauthenticated access would let other local processes bypass those safety checks. Auth is a prerequisite for trustworthy HITL.

> **Superseded.** `@sammorrowdrums/tool-cli` now binds a random port and issues a 32-byte session token; requests without `Authorization: Bearer <token>` are rejected. Authentication alone is not sufficient for trustworthy HITL, though — see [015](#015--mcppolicy-is-the-single-authorization-boundary-for-every-mcp-execution-path): an authenticated caller must still be re-authorized against the discovered, ungated tool set.

## 011 — Code mode uses `isolated-vm` for sandbox execution

**Date:** 2026-04-24
**Context:** Code mode (#4) lets the model write JavaScript to chain read-only MCP tool calls. The generated code runs in a sandbox. Options evaluated: Node `vm` module, `isolated-vm`, Deno subprocess, Cloudflare workerd, Pydantic/Python subprocess, WASM.
**Decision:** Use `isolated-vm` (V8 isolates in Node.js). Provides memory limits (128MB default), CPU timeouts (30s default), and V8-level isolation. Tool dispatch via `Reference` async callbacks — actual MCP calls execute on the host, never in the sandbox.
**Rationale:** Code mode has no HITL prompt (human-in-the-loop) because `McpPolicy` refuses any non-read-only tool from the `code-mode` source outright rather than asking — making sandbox security important. Node's `vm` module is documented as "not a security mechanism" and is escapable via prototype pollution. `isolated-vm` provides genuine V8-level isolation with ~15ms overhead — negligible vs MCP network I/O. Deno subprocess (400ms/call) and workerd are too slow or complex for interactive use.

## 012 — Code mode uses `ctx.eval` instead of `compileModule` for execution

**Date:** 2026-04-24
**Context:** Initial implementation used `isolate.compileModule()` + `module.evaluate()` for running sandboxed code with top-level await. Discovery: `module.evaluate()` resolves prematurely when multiple sequential `Reference.apply()` calls use `{ result: { promise: true } }` — the module evaluation promise resolves after the first async reference call, not after all code completes.
**Decision:** Use `ctx.eval()` with `{ promise: true, copy: true }` instead. Wrap user code in an async IIFE that returns the final result.
**Rationale:** `ctx.eval` with `promise: true` correctly awaits the full async IIFE, including all sequential tool dispatch calls. This is critical for code mode's chaining use case where the model writes for-loops calling multiple tools sequentially.

## 013 — Centralize MCP v2 negotiation, input, and terminal results

**Date:** 2026-08-24
**Context:** The monolithic MCP SDK v1 client could not provide negotiated 2026-era behavior, SDK-managed multi-round-trip input, or one lossless result contract across direct tools, Code Mode, and tool-cli.
**Decision:** Build every connection through one `@modelcontextprotocol/client@2.0.0` factory using automatic version negotiation, the public Streamable HTTP and stdio transports, and explicit `2026-07-28` support with legacy fallback. The seam advertises only form elicitation and an empty extensions declaration, bounds MRTR rounds and request time, and routes form input through mcpi's explicit UI. Every tool path receives one terminal `CallToolResult` adapter; protocol and transport failures remain thrown errors. Missing cache TTLs default to zero, and only SDK-managed tool-list change subscriptions are enabled.
**Rationale:** A single seam keeps identity, capabilities, negotiation diagnostics, pagination, timeout policy, and user-input safety consistent. Preserving the protocol result object prevents each execution path from dropping newer content blocks or scalar structured JSON. Immediately stale cache defaults avoid surprising reuse, while servers can still opt in with explicit cache hints. General subscription lifecycle and persistent cache ownership remain future host-level work.

## 014 — Code Mode separates discovery, schema survival, and dispatch permission

> **Superseded in part by [027](#027--code-mode-asks-instead-of-refusing-and-approval-posture-is-fingerprinted).** The dispatch-permission half of this entry was wrong. Code Mode no longer refuses non-read-only tools; it routes them through the same annotation-driven confirmation as every other surface. The discovery and schema-survival halves stand.

**Date:** 2026-08-24
**Context:** Code Mode registration and discovery were both gated by `readOnlyHint === true && outputSchema`, which disabled pure computation with zero MCP tools, hid non-read-only tools from discovery, and excluded safe legacy tools that omitted an output schema.
**Decision:** Register `code_execute` and `code_search` independently of MCP connectivity. Catalog every MCP tool and generate hints for all of them, but allow host dispatch only for tools with `readOnlyHint === true` and `destructiveHint !== true`. For callable tools lacking `outputSchema`, use a client-internal permissive schema with separate synthesized provenance; preserve declared schemas by reference and never add provenance to MCP traffic. Report declared/synthesized counts in diagnostics and hint headers. Refuse zero-callable `code_search` before isolate creation with `no_eligible_tools`, while keeping `code_execute` available for pure computation.
**Rationale:** Visibility is not authority. Keeping permission enforcement at the host dispatch boundary prevents generated code from invoking writes while still making the complete catalog understandable. The internal schema floor improves compatibility without pretending an unknown result is typed, and always-on execution preserves Code Mode's deterministic computation value even when MCP is unavailable.

## 015 — `McpPolicy` is the single authorization boundary for every MCP execution path

> **Amended by [026](#026--skill-references-are-exposure-not-authorization) and [027](#027--code-mode-asks-instead-of-refusing-and-approval-posture-is-fingerprinted).** The single-boundary decision stands and is the foundation of both. Two rules it originally carried were removed: skill gating is no longer part of the pipeline, and Code Mode's stricter refusal is gone. Skill approval is no longer a permission grant.

**Date:** 2026-08-24
**Context:** Four execution paths reached MCP independently: deferred/direct proxy tools, Code Mode dispatch, the tool-cli provider RPC, and skill resource reads. Each enforced a different subset of rules. `McpClientManager.callTool` verified only that a server was connected, never that the tool had been discovered. The tool-cli `ToolProvider` advertised every tool including skill-gated ones, and `ToolCliServer.callTool` forwards `server`/`tool`/`args` to the provider without a membership check, so an authenticated caller could name a hidden tool directly — the `tool_call` hook that gates mcpi dispatch never fires for RPC. `load_skill` unlocked an MCP server's `allowed-tools` with no user approval at all. Resource reads went straight to `client.readResource` with no origin isolation, so one server could serve another's `skill://` URI. Nothing recorded who initiated a call.
**Decision:** Introduce `McpPolicy` as the one dispatcher every path crosses exactly once. It owns connectivity checks, discovered-set membership, skill gating, argument validation against the declared input schema, annotation-driven HITL, cancellation checks, resource authorization, and an audit ring buffer. Each entry point tags its `source` (`proxy`, `code-mode`, `tool-cli`, `skill-discovery`, `skill-load`) and the policy applies the same ordered pipeline to all of them, denying before any upstream call. `createPolicyToolProvider` narrows tool-cli's view to the policy-visible set and re-authorizes each RPC call. MCP-origin skill grants require explicit user approval, keyed on server + resource URI + a hash of the sorted tool list, so widening `allowed-tools` or replaying a grant from another server re-prompts. A tool already unlocked by an approved grant is recorded as `reused` rather than prompted twice. Code Mode keeps its stricter rule: non-read-only tools are refused outright rather than confirmed.
**Rationale:** Enforcement duplicated across four call sites is enforcement that drifts; each path had already drifted. Collapsing to one boundary makes "unknown tools never reach upstream" and "HITL happens once" properties of the system rather than conventions. Denying before the provider call is what makes the tool-cli membership gap unexploitable without waiting on an upstream API change. Binding grants to origin and content means an approval authorizes a specific claim from a specific server, not a name. Recording source on every decision gives the audit log the one field it needs to be useful, and the `reused` outcome keeps a correct policy from degrading into prompt fatigue.

## 016 — Consume the draft skills extension behind a gate, verify every byte, and never mix contracts

> **Amended by [026](#026--skill-references-are-exposure-not-authorization) and [028](#028--negotiate-the-draft-skills-extension-by-default-and-say-that-it-is-draft).** Every verification rule here stands — digests, per-skill allowlists, contract separation, conservative caching. Two things changed: the gate now defaults on with an explicit opt-out, and the content fingerprint binds _exposure_ rather than an approval, because there is no longer an approval to bind.

**Date:** 2026-08-24
**Context:** Skill discovery relied on `skill://` resource URIs. A URI shape is not evidence: nothing proved that the SKILL.md a server returned at load time was the one whose frontmatter the host had shown the user at approval time, that a supporting file belonged to the skill being loaded, or that a server had not quietly rotated its content after approval. [SEP-2640](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2640) proposes `skills/list`, `skills/get`, and `resources/directory/read` with per-resource `{uri, digest, size}` declarations that make those questions answerable — but it is an unratified Draft on the Extensions Track whose wire format can still change, and `github/github-mcp-server` declares the extension name today while implementing none of its methods.
**Decision:** Implement the extension as a client pinned to revision `753b9f2be43e07fdd070e535d75f190cff14beea`, gated behind `experimental.skillsExtension` (or `--mcp-skills-extension`) and **off by default**, with a startup diagnostic naming the revision and status so draft support can never be mistaken for final support. Advertise the capability per request under SEP-2133 and re-resolve it from the server's declared capabilities immediately before every call — cache listing contents, never the right to ask. Verify size and raw SHA-256 on every read with no already-verified shortcut and no API that returns unverified bytes; enforce the 512-entry and 16 MiB limits from the entry alone before fetching; reject malformed or uppercase digests rather than normalizing them; reparse SKILL.md frontmatter and compare it field-by-field against the listing. Key read allowlists by `serverName` + `skillUri` so a file listed by one skill cannot be read while loading another and no skill can cause a read against a different server. Extend the `McpPolicy` grant key with a fingerprint of the resource set so rotation re-prompts, and rebuild `allowed-tools` at load time from the entry just served. Resolve names in a per-origin namespace, recording collisions instead of shadowing. Honour `ttlMs`/`cacheScope` conservatively — `session` and `connection` only, page 1 only, five-minute cap, never for truncated listings, never for `skills/get`. Keep legacy `skill://` discovery as a documented compatibility fallback used only when a server declares no extension; once a server declares it, serve that server from the extension path alone, including when the listing is empty and when the extension path throws.
**Rationale:** A pinned revision and a default-off gate are what let an unratified proposal be implemented honestly — the alternative is shipping something that reads as support for a spec that does not exist yet. Verifying on every read rather than once is the difference between checking a claim and trusting a name: the failure this protects against is a server that serves different bytes the second time, which any cached verdict would miss. The frontmatter reparse closes the same gap for the field the user actually read before approving. Per-skill allowlists narrow authority to what an entry declared, where a per-server index would grant a skill everything the server ever listed. Binding approval to a content fingerprint means the user approved a specific set of claims, not a name a server can later refill. And treating an empty listing as a fallback trigger would let any extension-declaring server silently downgrade the host to the weaker contract — the one case where mixing contracts is most attractive to an attacker and least visible to the user.

## 017 — One always-emitted execution-routing section describing facilities by task shape, never precedence

**Date:** 2026-08-24
**Context:** The extension told the model _how_ to use each mechanism but never _when to reach for which_, and the little cross-tier guidance that existed was wrong in two ways. `CodeModeManager`'s prompt appendix carried a `### Choosing the right approach` block comparing all three tiers — cross-facility policy owned by one facility's module. `tool-cli`'s section instructed the model to "prefer the skill", a fixed precedence that is false whenever no skill matches the task. Both were emitted only when MCP servers happened to be connected, so a session with zero servers received no routing guidance at all despite `code_execute` being fully usable for pure computation. Nothing mentioned bash, even though the only facility that can write a file is bash. Availability was communicated by silence: an unstarted tool-cli simply produced no section, which the model cannot distinguish from a facility it forgot about. The prompt tag `<tool_cli>` read like an action, and models responded accordingly — emitting `<tool_cli>…</tool_cli>` pseudo-calls and fabricated transcripts instead of invoking the bash tool.
**Decision:** Add `src/routing/` as the single owner of cross-facility guidance. It emits exactly one `<execution_routing>` section on every load, **including with zero MCP servers**, describing four facilities — Skills (domain workflow guidance), Code Mode (sandboxed exact computation and control flow, no fs/net/process), tool-cli (authenticated MCP-to-shell on-ramp invoked _through the host bash tool_), and bash + external programs (the filesystem/artifact/data-pipeline substrate) — each by task shape, with an explicit note that tool-cli and bash compose. `FACILITY_ORDER` is alphabetical by id, chosen precisely because alphabetical cannot be read as a ranking and renders byte-stable across turns. Every facility always reports `available` / `unavailable` / `unknown` with a non-empty reason: code mode is available with zero servers; skills report discovered count and draft-extension status; tool-cli is advertised only after its RPC server actually starts, and a startup failure is surfaced with a next step; bash comes from host tool registration via `getAllTools()`, with `unknown` reserved for "the registry could not be read" rather than conflated with absent. A started tool-cli with no bash tool renders unavailable — the one cross-facility coupling, because a healthy RPC server is unusable without a shell. The cross-tier block is deleted from `CodeModeManager`, `prefer the skill` is deleted from tool-cli's section, and every mechanism description including `load_skill`'s tool description now leads with `Use when`, with skills stating that declared tools are enabled only after approval. `<tool_cli>` is renamed `<tool_cli_usage_docs>` and states outright that the model must invoke the bash tool with a `tool-cli ...` command and must never emit XML/text pseudo-calls or fabricate output. `src/routing/seam.ts` feature-detects a future core `registerExecutionFacility` via an `in` check plus `typeof`, with no assertions, and otherwise emits the complete section from `before_agent_start`; the paths are mutually exclusive so the section is never duplicated. `src/routing/tripwire.ts` ships `detectToolCliTripwires` as a regression guard for pseudo-calls and narrated transcripts with no real bash call.
**Rationale:** Routing guidance that only appears when servers connect teaches the model that computation requires a server, which is false — the zero-server case is exactly when a model most needs to be told `code_execute` still works. Precedence rules are the wrong shape for this problem: "prefer the skill" is correct only when a matching skill exists, and a model that internalises it wastes turns looking for one. Task shape degrades gracefully where ranking does not. Silence about an unavailable facility is indistinguishable from an incomplete prompt, so an explicit unavailable line with a reason is strictly more information than omission — and for a tool-cli that failed to start, the reason is the only way the user learns something broke. Alphabetical ordering is a deliberate anti-affordance: any semantic order invites the model to read position as priority. Keeping cross-facility prose out of `CodeModeManager` matters because a facility describing its rivals will describe them from its own point of view, and the appendix is loaded exactly when Code Mode is in play. The tag rename is the cheapest available fix for a real observed failure mode — an action-shaped tag is an invitation, and `<tool_cli_usage_docs>` reads as reference material about a program, which is what it is. Building the seam now while implementing none of the core API keeps this change additive: if `registerExecutionFacility` lands, the fallback stops firing with no edit here.

## 018 — Verify tool-cli bridge v1 before exposure and authorize resources at the same boundary

**Date:** 2026-08-24
**Context:** Treating a listening tool-cli HTTP server as available proved too weak. A package/client major mismatch could leave an unusable CLI advertised; subprocess credentials were set before either side proved its contract; the bridge exposed no upstream MCP negotiation summary; cancellation stopped at the provider boundary; and v1 resource operations needed the same origin and skill isolation as tool calls. Legacy result mapping also risked dropping scalar `structuredContent`, newer content blocks, resource metadata, and binary blobs.
**Decision:** Depend conceptually on `@sammorrowdrums/tool-cli:^1.0.0` and implement bridge protocol v1. Start the server only when bash is in the host's active-tool set, then serialize and authenticate `getBridgeInfo` privately and require protocol major 1, the complete deterministic operation/capability set, a non-empty implementation version, and an upstream summary derived from current per-server MCP diagnostics. Pin handshake and agent CLI traffic to loopback so an inherited `TOOL_CLI_HOST` cannot receive the fresh bearer token. Mask inherited `TOOL_CLI_PORT`/`TOOL_CLI_TOKEN` values until a successful handshake exposes this session's credentials or emits usage docs, and strip every `TOOL_CLI_*` value from the safe environment passed to stdio MCP children. Startup, HTTP, RPC, timeout, transport, and compatibility failures keep credentials withheld and produce typed actionable diagnostics. The v1 provider exposes exact policy-visible tool objects, routes each call/list/template/read through `McpPolicy` once, forwards provider `AbortSignal` through policy to MCP v2, and preserves complete protocol objects with explicit `!== undefined` checks for optional falsey data. Ordinary resources are available, including binary `--out`; all case variants of the `skill://` scheme and every exact resource URI declared by a SEP-2640 skill remain hidden from tool-cli and direct reads are denied in favor of `load_skill`.
**Rationale:** A port number establishes reachability, not compatibility or authority. An authenticated versioned handshake makes availability a verified fact and turns major drift into an immediate startup diagnostic rather than a later shell failure. Delaying credentials removes the interval where an unverified bridge is callable. Reusing `McpPolicy` for v1 resources preserves the system's one-boundary invariant and prevents the CLI from becoming a back door into skill instructions or grants. Passing cancellation all the way to MCP v2 avoids expensive work surviving a disconnected CLI request, while lossless object forwarding keeps the bridge compatible with modern MCP additions and valid falsey JSON values.

## 019 — `directoryRead` is a server capability, so only the fixture that implements it declares it

**Date:** 2026-08-26
**Context:** A release audit flagged the SEP-2640 `directoryRead` capability as possibly over-claimed. The draft spec (pinned at rev `753b9f2be43e`) defines `directoryRead` inside `capabilities.extensions["io.modelcontextprotocol/skills"]` as a declaration made by **servers** in `initialize`, meaning "the server implements `resources/directory/read`", and requires that clients MUST NOT call that method against a server which has not declared it. mcpi-ext is a client, so it has no capability of its own to advertise here — but its in-repo fixture server registered a `resources/directory/read` handler unconditionally, including when configured not to declare the capability. Nothing in the test suite asserted what actually crossed the wire during `initialize`.
**Decision:** Leave the client read path unchanged — `src/mcp/client-factory.ts` was already spec-correct in gating calls on the declaration. Gate the fixture server's handler registration on the same flag that controls declaration, so the fixture cannot answer a method it did not advertise. Add `src/mcp/capability-wire.test.ts` to assert the negotiated `initialize` payload directly: that the extension key is absent when the contract is off, present-but-empty when declared without `directoryRead`, and carries `directoryRead: true` only when the handler exists.
**Rationale:** A capability is a promise about behaviour, and the only way to keep a promise honest is to test the bytes that carry it rather than the variable that produced them. Declaring a capability the implementation lacks is the failure mode the spec's MUST NOT is written to prevent; implementing one that is not declared is the mirror image — harmless to a compliant client, but it means the fixture cannot be used to prove a compliant client refuses the call. Gating both together makes the fixture a real test of the contract instead of a permissive stand-in, and asserting on the wire payload means a future refactor cannot quietly widen what the extension claims.

## 020 — `isolated-vm` is an optional dependency loaded lazily, and there is no `node:vm` fallback

**Date:** 2026-08-26
**Context:** `isolated-vm` is a native addon imported at the top level of the Code Mode executor. A top-level import makes it a hard install-time requirement for the whole extension: on any platform without a prebuild — notably Intel macOS, for which 6.2.x ships no `darwin-x64` binary — installation fails outright, taking skills, tool-cli, and execution routing down with it even though none of them need a sandbox. The audit also asked whether Node 24 was really supported, and whether `isolated-vm` 7.x could be pulled in on Node 22.
**Decision:** Move `isolated-vm` to `optionalDependencies` at `~6.2.0` and load it through `src/code-mode/isolated-vm.ts`, an adapter with no top-level import that resolves the addon on first use via `await import(specifier)` where `specifier` is a `const` variable rather than a literal. Model the result as `SandboxAvailability = { state: "available" | "unavailable" | "unknown"; reason }` and thread it through `code-mode/index.ts` → `routing/facilities.ts` so an absent addon renders Code Mode as unavailable **with the reason stated**, while skills, tool-cli, and routing continue unaffected. `code_execute` stays registered and refuses with `sandbox_unavailable`. Under no circumstance fall back to `node:vm`.
**Rationale:** `node:vm` is not a sandbox — it is same-isolate execution with a cosmetic global object, and untrusted code escapes it through constructor chains as a matter of routine. Silently substituting it would convert a visible unavailability into an invisible security hole, which is the worst possible trade for a facility whose entire purpose is isolation. Refusing loudly is the only honest option, and stating the reason turns an install-time failure into a runtime diagnostic the user can act on. Keeping `code_execute` registered rather than hiding it matters because registration happens synchronously at load while addon resolution is async: a truthful refusal beats concealing a facility that may in fact be working, which is why `unknown` is a real state and `isActive` treats it as active. Using a variable specifier keeps `tsc` from binding the build to whether the addon is installed, and structural interfaces rather than `import type … from "isolated-vm"` keep the published `.d.ts` free of any reference to it — asserted by the package verifier. The `~6.2.0` range is what keeps 7.x out: it cannot resolve to a new major. The `engines.node >=24.0.0` that 7.x declares is a weaker, secondary signal — npm emits `EBADENGINE` as a warning and installs anyway unless `engine-strict` is set — so the range is the guard and the engines field is only corroboration. Prebuilds cover `linux-x64`, `linux-arm64` (abi127/abi137, glibc and musl), `darwin-arm64`, and `win32-x64`; `node-gyp-build` picks the ABI at runtime, so a single install serves both Node 22 (abi127) and Node 24 (abi137). Intel macOS compiling from source is a documented gap, not a supported path.

## 021 — Peer on a bounded `>=0.85.0 <1.0.0` mcpi range, not `^1.0.0` and not `*`

**Date:** 2026-08-26
**Context:** v1 depends on host APIs that do not exist in the published mcpi (`0.70.9` on `latest` and on `main`). The obvious `^1.0.0` peer range was wrong on the facts: mcpi's release branches sit at `0.84.2`, so its next release is `0.85.0` — a `0.x` line, where each minor is a breaking boundary by SemVer convention. An unbounded floor (`>=0.85.0`) would accept a future mcpi `2.0.0` whose extension API this code has never seen.
**Decision:** Declare `peerDependencies: { "@sammorrowdrums/mcpi": ">=0.85.0 <1.0.0" }` — a floor at the first release carrying the required API and a ceiling at the next major. Use `>=0.70.9 <1.0.0` for the dev dependency (not `^0.70.9`, which would exclude `0.85.0`), pin `0.70.9` in the lockfile for deterministic `npm ci`, and have `scripts/release-check.mjs` refuse to publish while the floor is unavailable on the registry.
**Rationale:** A peer range is a claim about which hosts this code has been reasoned about against, and the honest claim here is "the 0.8x API, up to but not including the next major". `^1.0.0` names a version that does not exist and would never install. A bare floor silently opts into every future major, which is exactly the arbitrary-major acceptance the audit objected to. The consequence is that the floor is briefly unsatisfiable until `0.85.0` ships, so `verify-package.mjs` installs the host explicitly with `--legacy-peer-deps` and `release-check.mjs` fails closed — a release blocked on a missing peer is correct behaviour, not a defect. That check is skipped under `--offline` so CI can run the rest of the preflight without network.

## 022 — Publish a deliberately small surface, and prove the tarball rather than the working tree

**Date:** 2026-08-26
**Context:** Preparing the first publishable release surfaced a category of bug that no existing check could catch: the artefact a consumer installs is not the tree CI tests. Tests, test servers, and source maps would have shipped; README links were repository-relative and would have 404'd on npm; and nothing prevented a consumer from reaching past the entry point into `dist/mcp/policy.js` — turning internals into a de facto public API that any refactor would break. A `postinstall` build was not an option, since the release must install without a toolchain.
**Decision:** Split the build (`tsconfig.build.json` drops tests, test servers, and maps; `tsconfig.json` keeps them because integration scripts spawn `dist/test-servers/*`), add a `files` allowlist with negations as a second line of defence, and publish an `exports` map that exposes only the root entry and `./package.json`. Rewrite every README link to absolute `blob`/`raw` URLs. Add `scripts/verify-package.mjs`, which builds the release output, packs it, asserts the tarball's contents, installs the tarball **and a host** into a clean throwaway project, and then drives the installed artefact: exports resolve, deep imports fail with `ERR_PACKAGE_PATH_NOT_EXPORTED`, tool-cli is `1.0.2` and the MCP client exactly `2.0.0`, zero-server routing renders, `code_execute` runs, deleting `node_modules/isolated-vm` degrades to a stated reason rather than a crash, and both discovery contracts — legacy `skill://` and draft SEP-2640 — negotiate correctly.
**Rationale:** Every packaging failure in this list is invisible from inside the repository and obvious from outside it, so the only test that can catch them is one that leaves. Installing a host alongside the tarball is not incidental: `parseFrontmatter` and `stripFrontmatter` are **value** imports from `@sammorrowdrums/mcpi`, so the host is a runtime dependency and `npm install <tarball>` on its own would pass while a real consumer's import failed. Blocking deep imports is what makes the internal boundary real — an `exports` map is the only mechanism that turns "please do not import this" into an error at resolution time, and it is far cheaper to widen later than to narrow after someone depends on it. The isolated-vm deletion step exists because a degradation path that is never exercised is a claim, not a behaviour.

## 023 — Gate the release on a clean production tree, and accept one unfixable dev-only advisory explicitly

**Date:** 2026-08-26
**Context:** The release audit listed 18 dependency findings (1 low, 5 moderate, 12 high) and asked that they be resolved through supported upgrades without removing functionality, with the production tree clean or the residue precisely justified. Most were dev-tree transitives resolvable by upgrading. One was genuinely in the production tree: `fast-uri@3.1.2` (high), reached via `@sammorrowdrums/tool-cli@1.0.2 → ajv@8.20.0` — a transitive we do not control and cannot fix by bumping a direct dependency, since tool-cli must stay pinned at `^1.0.2` for the verified bridge-v1 handshake.
**Decision:** Upgrade what upgrades cleanly, and add a narrow `overrides` block for the rest: `fast-uri: ^3.1.5` and `@anthropic-ai/sdk: >=0.91.1`. Gate CI on `npm audit --omit=dev --audit-level=low`, which must exit zero, and run the dev audit as advisory-only. Accept exactly one residual finding — `extract-zip`, GHSA-jmr9-qjv8-65gv / CVE-2026-56876, high, symlink path traversal — reported twice because it is also surfaced through its dependent `@sammorrowdrums/mcpi`.
**Rationale:** The advisory's vulnerable range is `<= 2.0.1`, and `2.0.1` is the newest version ever published, so `fixAvailable: false` is a fact about the ecosystem rather than a stale lockfile: there is no upgrade to take, and the only "fixes" available would be removing the host from the dev tree or forking a transitive — both of which trade a theoretical dev-time risk for real lost functionality. It reaches the tree solely through the dev/peer host and is absent from the production tree, which the `--omit=dev` gate proves rather than asserts. The exploit path also requires extracting an attacker-supplied archive, which is not something this package's build or test path does. Two audit thresholds are deliberate: production is gated at `--audit-level=low` because anything shipped to consumers should be defensible at any severity, while the dev tree is reported and not enforced because a build cannot be held hostage to a transitive with no available fix. Recording the accepted set here — rather than suppressing it in tooling — keeps the decision reviewable, so if `extract-zip` ever ships a fix the residue is visibly one line rather than silently zero.

## 024 — Pin test collection globs explicitly rather than inheriting tool defaults

**Date:** 2026-08-26
**Context:** The repository had no `vitest.config.*` at all, relying on Vitest's defaults. Vitest 4 narrowed `defaultExclude` to `node_modules` and `.git`, dropping the `dist` entry that earlier versions supplied. Because the dev `tsconfig.json` deliberately compiles test files into `dist/` — integration scripts spawn `dist/test-servers/*`, so it cannot simply stop — every suite was collected twice whenever a build existed: once from source and once from the compiled JavaScript beside it. The CI test job builds before it tests, so half of what CI reported as passing was stale output. The defect was invisible in a clean checkout and only appeared as an implausible test count (62 files / 900 tests against an expected 31 / 450), which is precisely the kind of signal that gets read as "more coverage" rather than "same coverage, twice, half of it stale".
**Decision:** Add a `vitest.config.ts` pinning `include: ["src/**/*.test.ts"]` and an `exclude` that names `dist/**` explicitly, and guard both invariants with `src/vitest-config.test.ts`. The guard reads the config file from disk with `node:fs` rather than importing it, and the compiled artefacts `vitest.config.js`/`.d.ts` are gitignored.
**Rationale:** A default that has already changed once under us is not a foundation to build on; naming the globs costs four lines and removes an entire class of silent drift. The guard is `fs`-based for a concrete reason rather than a stylistic one: an import-based assertion was written first and **passed against a deliberately regressed config**, because vitest resolves its own config through a cache and — more seriously — a compiled `vitest.config.js` at the repository root takes precedence over the `.ts` source, so the run and the assertion were reading different files. That shadowing is a trap rather than a nuisance, which is why the compiled copies are ignored rather than merely deleted. The `fs`-based guard was verified to fail all three assertions under the same regression that the import-based one passed, so it is known to be capable of failing — a guard that has never been seen red is an assumption, not a test.

## 025 — Managed packages declare their entry point and never require a second host copy

**Date:** 2026-09-08
**Context:** mcpi's managed npm root deliberately installs with peer resolution disabled: extension packages execute inside the existing host, and auto-installing another `@sammorrowdrums/mcpi` can create duplicate module identities and block host upgrades. mcpi-ext nevertheless imported two frontmatter helpers from that peer as runtime values. Its package also omitted the `pi.extensions` manifest that managed resource discovery reads; `main` and `exports` make Node imports work but do not declare an mcpi resource.
**Decision:** Declare `pi.extensions: ["./dist/index.js"]`. Keep `@sammorrowdrums/mcpi` as the bounded host compatibility peer and use it only for erased TypeScript types. Vendor the host-compatible frontmatter helper implementation in mcpi-ext and pin its actual parser, `yaml@2.9.0`, as a direct runtime dependency. Extend the release verifier to install the tarball without peers and to drive a clean public mcpi 0.85.1 managed install under the Node 22/24 package matrix, including list, exact managed-path import, help flags, absence of a duplicate host, and zero-server RPC startup.
**Rationale:** Package metadata, Node resolution, and host resource discovery are separate contracts and all three must be true. An explicit resource manifest is the only reliable way for a compiled root entry to be discovered. A peer expresses which host may invoke the registrar; it must not be used as an ordinary library dependency when the package manager intentionally withholds it. Owning the tiny parsing adapter and its real dependency keeps one host instance authoritative, preserves the existing parsing semantics, and makes the tarball independently importable in the same filesystem layout users receive.

## 026 — Skill references are exposure, not authorization

**Date:** 2026-09-10
**Context:** Skills had become an access-control mechanism by accident. A skill's `allowed-tools` was treated as a permission grant: `load_skill` prompted the user to approve it, a `tool_call` hook refused any call to a skill-referenced tool until its skill was loaded, and `McpPolicy` carried a skill check in the pipeline every call crossed. Four things followed, all bad. Deferred direct proxies were rejected at dispatch even when the provider's own grammar permitted the call, so a legitimate call failed with an error telling the model to load a skill it had no reason to load. Code Mode and tool-cli — which the model can reach without any skill at all — were refused tools they had every right to call, turning a composable surface into a fallback chain. The user was asked to approve _reading a schema_, which is not an action and cannot be harmful, training them to click through prompts that never carried a decision. And separately, activation was a silent no-op in production: `load_skill` reported revealed tools in a `details.activatedTools` field that the host never reads, while the field it does read, `ToolResultMessage.addedToolNames`, was never populated — so a user could approve a grant and see nothing change.
**Decision:** Delete the skill gate from `McpPolicy` entirely and delete the `tool_call` hook. Deferral is visibility on the direct proxy surface and nothing else: `deferred: true` at registration, with the host's `splitDeferredTools` keeping definitions out of the model's view while leaving them in the grammar. `load_skill` returns the skill body and sets `addedToolNames` directly on its `AgentToolResult`, so the host emits `tool_reference` blocks on the conversation tail — the registered tools array and the system prompt are never mutated, and the prompt prefix stays byte-identical for the whole conversation. `activateSkillGrant` becomes `activateSkillReference`, returns `activated`/`reactivated` with no declined case, and never prompts. Names that match no discovered tool reveal nothing and are surfaced as `unresolvedTools` diagnostics. Origin binding and content fingerprinting are kept in full, repurposed to decide _which definitions_ activate rather than whether anything may run. Resource authorization is untouched: `skill://` URIs stay origin-bound, per-skill resource allowlists stay exact, and a discovery pass still cannot authorize a skill-load read.
**Rationale:** Conflating "not yet shown" with "not allowed" is the root error, and it produces harm in both directions. It refuses calls that were always legitimate, and it makes an approval prompt appear at a moment when nothing is at stake — which is worse than no prompt, because a prompt that never guards anything teaches the user that prompts do not guard anything. Authorization belongs where the effect happens: at execution, from annotations, identically on every surface. Once that is true, `allowed-tools` can be exactly what a server author means by it — a reading list — and widening it cannot escalate anything, because each revealed tool still faces its own confirmation when called. Keeping the fingerprint despite dropping the approval is deliberate: content binding was never really about permission, it was about making sure the definitions revealed are the ones the server publishes now. And emitting on the field the host actually reads is what makes any of this observable; the previous design was not merely wrong in principle, it did nothing at all.

## 027 — Code Mode asks instead of refusing, and approval posture is fingerprinted

**Date:** 2026-09-10
**Context:** A non-read-only tool called from the sandbox was denied outright, never escalated to a prompt, on the reasoning that "visibility is not authority". The sandbox could therefore see and describe work it could never perform, and the user was never offered the decision. The rule also duplicated: `isEligibleForCodeMode` in `eligibility.ts` was a byte-identical copy of `isReadOnlyToolCall` in the policy, and a third copy existed in the Code Mode catalog work — one security classification expressed three times, where a divergence surfaces as the sandbox silently skipping an approval the boundary meant to raise.
**Decision:** Remove the unconditional `code-mode` denial. A write or destructive tool called from inside a script pauses at the same `McpPolicy` confirmation any other source raises and resumes with the value it returns; a decline surfaces as a legible error naming the tool and saying how to proceed. Exactly one audit record per call, tagged `code-mode`, on both paths. Delete the duplicate predicates rather than renaming them, and have the catalog ask the policy. Because the catalog's `definitionDigest` fingerprints approval posture, express that posture as a closed four-value classification — `read_only`, `write`, `destructive`, `contradictory_annotations` — with a deduplicated, canonically ordered reason set and a versioned serialization drawn entirely from closed vocabularies. Sandbox restrictions are untouched and remain separate: no fs, no network, no process.
**Rationale:** Refusing looked conservative and was not. It removed a decision from the only party entitled to make it, and it did so at precisely the moment the user had the most context — mid-script, with the arguments visible. The prompt is the safety mechanism; skipping it is not extra safety. On the fingerprint: `runsUnattended` is a boolean, so an ordinary write and a destructive one are the same byte, and a digest over it is blind to a tool acquiring `destructiveHint` — the single transition an approval fingerprint most needs to catch. Keeping `contradictory_annotations` distinct from `destructive` follows the same logic one step further: fold them and a tool losing its `readOnlyHint` while already destructive produces no digest change at all. Serializing from closed enums means no server-controlled string reaches the digest, so no tool name can be chosen to collide with a delimiter or impersonate another posture, and versioning the vocabulary makes a future change invalidate snapshots instead of colliding with them.

## 028 — Negotiate the draft skills extension by default, and say that it is draft

**Date:** 2026-09-10
**Context:** [016](#016--consume-the-draft-skills-extension-behind-a-gate-verify-every-byte-and-never-mix-contracts) gated SEP-2640 off by default, so a server that declared `io.modelcontextprotocol/skills` and served a complete, correct skill set was silently ignored unless the user knew to pass `--mcp-skills-extension`. The failure mode is the worst available: nothing is broken, nothing is logged, the feature simply does not exist for anyone who did not already know about it. Draft status was being managed by hiding the feature rather than by disclosing the status.
**Decision:** Negotiate by default. `experimental.skillsExtension` and the new `--no-mcp-skills-extension` flag are an explicit opt-out; `isSkillsExtensionEnabled` returns true unless the value is exactly `false`. The old `--mcp-skills-extension` flag stays registered as a documented no-op so existing command lines keep working, and is removed from the documentation so nobody learns it. Whenever the contract is in use, a visible diagnostic names the pinned revision and its draft status. Per-server behaviour is unchanged and remains the harder guarantee: support is re-resolved from each server's declared capabilities immediately before every request, so a server that never declared the extension is never advertised to or spoken to in it, whatever the default is.
**Rationale:** Default-off protects the client from a changing wire format by ensuring nobody uses it, which is not protection so much as absence. The actual risks — a spec that may change, a server that declares the name without implementing the methods — are already handled where they occur: by pinning a revision, verifying every byte, re-resolving capability before each request, and refusing to mix contracts. What default-off added on top of that was not safety but silence. Disclosure is the honest instrument for draft status: say it is a draft, name the revision, and let a user who does not want it turn it off. Keeping the dead opt-in registered rather than deleting it is the same principle applied to the upgrade path — an unknown-flag error would be a worse outcome than a no-op for a user who copied a working command line from the old docs.

## 029 — Pin the Code Mode prompt at session start, and pay for schemas only when asked

**Date:** 2026-09-09
**Context:** The released extension rendered every discovered MCP tool's full TypeScript signature into the system prompt, and `src/index.ts` re-rendered that section on every turn. Measured against the real 85-tool `github-mcp-server` surface with `GITHUB_TOOLSETS=all`, that was 33,133 tokens of tool declarations resent each turn, growing linearly with every server the user adds. `codemode.describeTools()` existed but was a stub, so the progressive path the design assumed was not merely unused — it was not implemented. The eager catalog also destroyed prompt-prefix caching: any server reconnecting, any tool list changing, invalidated the prefix for the rest of the session.
**Decision:** Render a declaration-only namespace block once, at session start, via `pinPromptSnapshot()`, and never re-render it. Exact schemas are fetched on demand through structured `code_search` operations — `browse`, `list`, `search`, `describe` — which return compact deterministic text into the conversation rather than into the tool definitions. A catalog change after pinning logs a diagnostic; late servers remain fully searchable and callable but never mutate the prompt. Gates in `prompt.test.ts` hold the section at zero per-tool tokens, ≤1,500 tokens per namespace block, ≤6,000 for the section, and require the block's SHA to be invariant under tool addition and removal.
**Rationale:** A prompt that changes when a server reconnects is a prompt that cannot be cached, and the cost of the eager catalog was therefore paid twice: once in tokens and once in lost prefix reuse. Fetch-on-demand is only defensible if retrieval actually works, which is why `retrieval.test.ts` gates it on the same 85-tool surface rather than a synthetic sample — the model's fallback when search fails is to enumerate, and enumeration is the eager catalog again, bought one page at a time. Namespaces are rendered **only** from declared sources — server `_meta`, or operator configuration — never inferred from tool names: leading-token grouping on the real fixture yields verbs (`list` 21, `get` 20) and head-noun grouping yields a 12-of-33 singleton tail (`branche`, `or`, `me`, `sub`). Garbage in a cached prompt prefix is permanent; the same garbage in a search result is discarded after one turn.

## 030 — Tool identity is a structured record, and an ambiguous reference resolves to nothing

**Date:** 2026-09-09
**Context:** Tools were addressed by a canonical string ref, `${server}/${tool}`. Tool names are chosen by the MCP server, which is exactly the party the policy boundary exists to distrust. A server registered as `a` shipping a tool named `b/echo` produces the ref `a/b/echo` — byte-identical to what server `a/b` shipping `echo` produces. Because authority round-tripped through that string, a server could name a tool such that a call intended for another server's tool resolved to its own.
**Decision:** Authority travels as a structured `ToolIdentity` (`{ serverName, toolName }`), and dispatch takes a `ToolTarget` union that distinguishes an identity from a human-typed ref. Index tools under a length-prefixed `identityKey(server, tool)` = `${server.length}:${server}/${tool}`, which no other pair can forge. Track a `collidingRefs` set; a ref that two identities could produce resolves to **neither**, returning `ambiguous_tool` with both candidates.
**Rationale:** Refusing an ambiguous reference is the only safe resolution, because both readings are equally well-formed and picking either silently — first-indexed, or most-recently-registered — hands the choice to registration order, which the attacking server can influence. Length-prefixing is what makes the key unforgeable rather than merely unlikely to collide: `"1:a/b/echo"` and `"3:a/b/echo"` differ regardless of what a server names anything. Refusal is also the cheaper failure: a legitimate collision surfaces immediately as an error naming both candidates, where a silent mis-resolution surfaces as a tool call that did the wrong thing to the wrong server.

## 031 — One frozen catalog per run, with an optional caller-supplied pin

**Date:** 2026-09-09
**Context:** Discovery calls made from inside a running script read the live catalog, while dispatch had already resolved against whatever was current when the run began. A server reconnecting mid-execution therefore produced a run that described one schema and called another — a time-of-check/time-of-use gap inside a single script. Separately, the ordinary case of describing a tool in one turn and calling it in the next had no protection at all: the schema could change in between, and arguments would be validated against a shape nobody had looked at.
**Decision:** Capture one `CatalogSnapshot` at the start of each run; every discovery, alias binding, and dispatch in that run reads that exact snapshot. `code_search` returns its `snapshotId`, and `code_execute` accepts it as an optional pin, failing `stale_snapshot` **before** the isolate is spawned. Track two fingerprints: `schemaHash` over the execution contract (input and output schema plus provenance), and `definitionDigest` over everything the model can read — identity, namespace, title, description, both schemas, annotations, `_meta`, callability. A tool described earlier with a different `schemaHash` fails `schema_changed` with instructions to re-describe.
**Rationale:** Two hashes because they answer different questions. `schemaHash` asks "would this call still be valid?"; `definitionDigest` asks "is the model still reading what it read before?" — and a server can rewrite a description into an instruction without touching a single schema, so a digest over schemas alone would miss the more interesting attack. The pin is optional rather than mandatory because a first call has nothing to pin, and refusing it would force a discovery round-trip on every script including ones that touch no tools. `schema_changed` is a distinct error rather than a generic failure specifically so the model does not retry: identical arguments against a changed schema cannot start working, and an error that invites a blind retry produces a loop instead of a recovery.

## 032 — Skill gating decides what may be called, never what may be found

**Date:** 2026-09-09
**Context:** Skill-gated tools are hidden from the model's tool list until a skill grant is approved. It was tempting to apply the same filter to Code Mode's catalog, on the reasoning that a tool the model cannot call is noise in search results. That would have made the catalog a function of session history: identical queries would return different results depending on which skills happened to have been loaded.
**Decision:** Index and rank every tool the gateway exposes, gated or not. Gating is enforced at dispatch, by `McpPolicy`, which is where it was always enforced. Lock this with a regression test asserting that the same query before and after `activateSkillGrant` returns **byte-identical** hits and ranking, including a control tool (`d42_search_regression`) that no skill references. Tenant-denied tools never reach the gateway at all, so denial is absence rather than demotion.
**Rationale:** Visibility is not authority — the policy boundary already refuses the call, so filtering search adds no safety and removes a true statement about what exists. The failure it prevents is concrete: a tool hidden from search that the policy would have permitted is a capability the model cannot discover it has, and its recovery is to guess. Byte-identity rather than set-equality is deliberate: if activation could merely reorder results, the catalog would stop being a stable thing to reason about across turns, and a model that learned a ranking in one turn would be misled in the next. The control tool exists because set-equality tests pass trivially when the gated tool is the only one that moves.
